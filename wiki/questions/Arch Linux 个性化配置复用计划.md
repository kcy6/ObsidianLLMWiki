### 文件只能由一个模块写入

Niri配置及会话自启动由niri-session统一负责；Waybar、输入法、锁屏模块只声明集成需求，不分别sed追加同一份config.kdl。terminal只拥有终端配置，浮动终端窗口规则归niri-session。通用GTK/Qt偏好归appearance，Waybar/Kitty/输入法各自的应用配色仍由对应模块维护。

桌面组合profile选择六个模块并解析依赖；单装terminal不强制安装Niri。按模块选择生成相应的Niri集成，不能在未选择Waybar或输入法时留下必须启动的缺失命令。本机现有clipse、awww、waypaper等调用也要登记；首版可选模块未实现时，明确保留/跳过处理，不能把整个当前Niri文件当作依赖闭合的通用配置。

### 实施批次与完成条件

1. **P0：固定当前配置基线。** 在独立工程保存首版白名单配置与资源，记录来源指纹；提取字体、包、外部命令、服务和硬件参数；只读采集不替换本机。暂用项目名arch-personal-setup，具体存放位置未创建，不在学习仓库或Wiki来源子模块内另建混合项目。
2. **P1：公共能力＋terminal闭环。** Shell入口、模块选择、默认plan、包渠道检查、逐文件差异、权限、持久备份、失败退出、部署记录和恢复。临时HOME测试覆盖含空格路径、已有文件/符号链接冲突、备份失败不改目标、重复执行与用户后续改写冲突。
3. **P2：waybar＋niri-session＋desktop-integration。** 参数化背光/显示器；集中生成集成入口，校验后应用。优先保留现有普通浮动终端及GNOME门户目标；不自动重建旧补丁或搬入未选模块。验证顶栏、快捷键、自启动去重、终端菜单入口与文件选择器。
4. **P3：input-method＋lockscreen。** 收录实际主题资源和授权信息，区分界面配置与私人词库；检查effects支持参数，再做可恢复环境的人工解锁测试。完成后六个模块才构成首版桌面profile。
5. **P4：扩展可选模块。** 外观、应用、Rust、虚拟机、代理等按依赖与需求逐步接入；系统服务和硬件功能分别验收。

每个模块完成条件一致：文件与依赖清单齐全、手动路径明确、plan可审阅、应用前备份、重复运行不重复追加、失败状态可追溯、恢复验证通过、Wiki链接唯一配置来源。包安装/服务改变与文件恢复分别记录，不承诺一次恢复自动撤销所有系统升级。

### 候选目录与单一维护位置

下面是普通 Git 阶段的设计草案，**不是已经创建的工程，也不是 chezmoi 原生目录规范**。若选 chezmoi，采用其源状态命名和模板规则，不再并行维护第二份 home 模板。

```text
arch-personal-config/
  README.md                # 支持范围、入口、对应Wiki链接
  manifest.yaml            # 模块、目标路径、权限、资源与依赖
  home/                    # 白名单内的普通配置文件
  hosts/                   # 显示器、缩放、背光等机器差异
  packages/                # 按模块区分官方包、AUR、Flatpak等
  system/                  # /etc 的审阅模板与服务声明
  scripts/                 # 将来实现采集、预览、应用、验证、恢复
  tests/                   # 临时HOME和VM验收
```

备份和部署日志保存在工程外的持久位置；.cache不作为唯一恢复来源。每个模块声明来源路径、目标路径、是否生成物、权限、需要的包、应用方式、验收及恢复方式。系统配置与用户配置分开，不能把全部脚本都以root运行。

通用偏好、机器差异、私人数据分别处理：主题与快捷键可复用；输出名称、缩放、GPU与背光按机器确定；SSH私钥、令牌、节点和登录状态进入独立私人备份。Git即使设为私有也不等于加密备份。动态生成的主题应保存模板和生成规则，生成结果只在需要复现快照时单独标注。

### 日常改动和新机复用

1. **先允许继续编辑原位置配置。** 修改一个模块，验收后把白名单内差异采集回工程，人工审阅并提交；这是普通 Git 阶段选定的单向流程。新机部署才从工程写入目标，避免自动双向覆盖。
2. Wiki 只更新有意义的原因、入口和操作变化，链接配置工程的路径与版本；不要每次把完整配置再粘进多篇指南。
3. 若选择 chezmoi，改用其 edit/diff/apply 流程；在原位置手动修改后需显式重新收录，不能假定会自动同步。
4. 新机先满足可启动、联网和目标用户条件，选择模块与主机配置，预览文件差异、待安装包和服务变化，再分阶段应用。
5. 应用前保存原文件、权限及“原本不存在”的记录；失败返回非零并停止依赖阶段。恢复只操作本次清单内且未被后续用户改写的文件，遇到改写先报告冲突。配置恢复不自动回退软件包和服务。
6. 先在临时 HOME 检查路径、权限和重复执行，再在可恢复VM验证通用桌面，最后验证显示器、亮度等实机项目。通过后记录工程提交、主机范围和验收日期。

“保存所有个性化”应先表现为**覆盖台账**：每项标记已收录、待调查、仅备份或明确排除。除配置文件，还盘点用户脚本、字体/主题/壁纸、desktop覆盖、MIME默认应用、用户与系统服务、选择性的gsettings/dconf键及/etc改动；不能从包清单反推出这些内容，也不能把当前配置可靠地归因到某次历史会话。

优先从 Kitty/Zsh/Starship 开始，再做 Niri/Waybar，随后输入法、主题、锁屏和桌面入口；代理、系统服务及硬件覆盖后置。每完成一组再扩展，不以“全机一键复制”作为首次里程碑。

## 后续实施顺序

1. 明确新机前置条件：已能启动和联网、目标用户、桌面选择、硬件类别，以及哪些个性化功能必须保留。
2. 只读采集当前生效配置，按白名单整理文件、权限、资源、包依赖、服务和启动入口；区分通用偏好、主机覆盖与私人数据。
3. 先形成逐模块参考文档：用途、前置条件、手动操作、配置清单、验收、回退。再按重复操作量决定采用单脚本或模块化工程，不预设工具框架。
4. 如制作脚本，要求默认预览、按模块选择、明确应用动作、覆盖前备份、可重复执行、失败记录及恢复入口；输出差异，保留目标机既有配置。
5. 在虚拟机或可恢复的新装系统验证通用模块，再验证实机硬件模块；记录提交、目标环境、操作结果、功能验收与回退结果。

## 配置边界与验收

- 通用偏好与主机参数分开：显示器名称、分辨率、缩放、背光设备、GPU、网卡、用户名和路径均需适配。
- 不把 1062 个包或 146 个显式安装项直接整体重装；先选模块，再解析依赖与安装来源。历史版本用于追踪，不默认要求新机锁定全部旧版本。
- 密钥、令牌、浏览器/聊天登录数据与网络凭据不进入可发布模板；保留需用户在新机完成的登录和授权步骤。
- 系统分区、引导器、驱动与快照布局作为单独的主机配置范围，不混入桌面偏好复制。
- 验收涵盖：登录桌面、终端与快捷键、字体/主题/壁纸、通知与认证、中文输入、门户/文件选择/屏幕共享、音频、亮度/锁屏，以及所选应用启动。未选择的模块不计入必验项。
